# Ticket: Stand up Supabase as managed PostgreSQL for SmartMatch

## Context

Postgres 16 runs in Docker for dev (`docker-compose.yml` `db` service) and on the
pilot VM (`docker-compose.vm.yml`). The only backup mechanism is the deploy-time
`pg_dump` in `scripts/vm/deploy.sh` — same-disk, deploy-triggered only, no
restore automation. Supabase gives us managed Postgres with real backups while
keeping the entire `smartmatch_persistence` layer unchanged. We use Supabase as
managed Postgres only — no PostgREST Data API, no GoTrue, no RLS. Authorization
stays in `smartmatch_authz`; the app connects as a direct Postgres client.

## Scope

- **In scope** — Supabase project for dev; connection config; migration + seed
  procedure; runbook; backup/maintenance SOP; debugging guide.
- **Out of scope** — moving the pilot VM's database (follow-up ticket), Supabase
  Auth/Storage/Edge Functions, schema changes, Firebase.

## Required reading — point devs and agents here first

- `python/smartmatch_persistence/smartmatch_persistence/schema.py` —
  hand-written mirror of the migrated schema (~49 tables). `postgresql.JSONB`
  columns, named constraints that `ON CONFLICT ON CONSTRAINT` targets by name,
  `ltree` columns on `org_unit.path` and `membership.granted_path`.
- `python/smartmatch_persistence/smartmatch_persistence/engine.py` — engine
  construction; `SMARTMATCH_DB_POOL_SIZE` / `_MAX_OVERFLOW` / `_POOL_TIMEOUT` /
  `_POOL_RECYCLE`; `pool_pre_ping=True` already handles idle-connection drops.
- `db/migrations/env.py` — reads `SMARTMATCH_DATABASE_URL`;
  `transaction_per_migration=True` (ADR-0009); migrations are hand-written,
  never autogenerated.
- `db/migrations/versions/` — 36 revisions, `0001_foundation_baseline` →
  `0036_host_organization`.
- `Makefile` — `db-up`, `migrate`, `migrate-check`, `seed-pilot*`,
  `verify-pilot-dataset`; `SMARTMATCH_DATABASE_URL` default at line 12.
- `tests/integration/test_schema_matches_migration.py` — the drift guard;
  compares `schema.py` against a live migrated DB in both directions. This is
  the acceptance test that Supabase matches the contract.
- `tests/integration/conftest.py` — integration test DB wiring.
- `docker-compose.yml` (`db`, `migrate`, `seed*` services) and
  `scripts/vm/deploy.sh` (the existing `pg_dump` pattern to reuse).
- `services/api/smartmatch_api/errors.py` — the stable error envelope; DB
  detail is deliberately never leaked to clients, so DB debugging happens in
  logs.
- `docs/operations/deploy-runbook.md` — "When a revision fails part-way";
  forward-only migration policy.

## Setup procedure (SOP draft — to become `docs/operations/supabase-setup.md`)

1. **Create project** — Supabase dashboard, region closest to the VM/users.
   Record project ref.
2. **Verify Postgres major version** — must be 16 to match
   `postgres:16-bookworm` in compose and CI. If the project provisions a
   different major, stop and decide: version bump is its own ticket.
3. **Verify `ltree`** — migration `0001` already runs
   `CREATE EXTENSION IF NOT EXISTS ltree` (verified at
   `db/migrations/versions/0001_foundation_baseline.py:56`), so a clean
   `alembic upgrade head` enables it. Confirm post-migrate with
   `SELECT * FROM pg_extension WHERE extname = 'ltree';` — the drift test
   asserts the GiST indexes on the two `ltree` columns, so a missing extension
   fails loudly.
4. **Choose the connection string deliberately** —
   - Session pooler (`aws-0-<region>.pooler.supabase.com:5432`) or direct
     (`db.<ref>.supabase.co:5432`) — both work with psycopg.
   - Do **NOT** use transaction-mode pooler (port 6543). `seed_pilot.py` takes
     a PostgreSQL advisory lock (`pg_advisory_xact_lock`) and psycopg's
     prepared statements are per-connection state; transaction pooling breaks
     both and raises "prepared statement already exists" errors.
   - Direct connections on Supabase are IPv6-only on newer projects — if the
     VM/host is IPv4-only, use the session pooler. This is the most common
     "it won't connect" cause.
5. **Set `SMARTMATCH_DATABASE_URL`** —
   `postgresql+psycopg://postgres.<ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres`.
   Password goes in the gitignored `.env` / Secret Manager — never committed
   (`.env.example` convention; CI secret-scans all refs).
6. **Tune the pool down** — Supabase plans cap direct connections well below
   postgres:16's `max_connections=100`. Set `SMARTMATCH_DB_POOL_SIZE` /
   `SMARTMATCH_DB_MAX_OVERFLOW` per the plan's limit; the engine defaults
   (20+10 per process) assume a dedicated Postgres.
7. **Migrate** — `cd db && alembic upgrade head` (or `make migrate` with the
   env var set). Forward-only; a failed revision leaves earlier ones applied —
   see ADR-0009.
8. **Verify parity** —
   `pytest tests/integration/test_schema_matches_migration.py -m integration`
   against the Supabase URL. Must pass both directions.
9. **Seed** — `make seed-pilot`, `seed-pilot-principals`, `seed-pilot-logins`
   (needs `SMARTMATCH_PILOT_*` pairs in `.env`), then
   `make verify-pilot-dataset`.
10. **Smoke** — `scripts/compose_smoke.sh` path or `make test-integration`
    against the Supabase DB.
11. **Lock down the Supabase surface** — do not distribute anon/service keys to
    the app; do not enable RLS policies expecting PostgREST access; the DB is
    reached only via `SMARTMATCH_DATABASE_URL`.

## Maintenance SOP (to become `docs/operations/supabase-maintenance.md`)

- **Migrations** — always `alembic upgrade head` against the Supabase URL;
  never downgrade; never autogenerate. Take a `pg_dump` first, reusing
  `deploy.sh`'s pattern (`pg_dump --clean --if-exists | gzip`).
- **Backups** — confirm the plan tier's backup schedule (daily on Pro; PITR is
  an add-on). Regardless of tier, keep a scheduled logical `pg_dump` to
  off-site storage (GCS) — Supabase backups are for disaster recovery, not for
  pulling a copy to a dev machine.
- **Schema changes** — edit a new hand-written revision in
  `db/migrations/versions/` AND mirror it in `schema.py`; the drift test fails
  the build if only one side moves.
- **Password rotation** — rotate the DB password in Supabase, update
  `.env`/Secret Manager, restart services. No code change.
- **Version upgrades** — Supabase Postgres upgrades are a ticket, not a click:
  run `migrate-check` and the drift test against a staging project first.
- **Monitoring** — watch pooler connection count vs. plan limit;
  `pool_pre_ping` covers idle drops but not exhaustion.

## Debugging guide — error codes and where to look

### API layer (envelope from `errors.py`; safe to branch on `code`)

- `unauthenticated` (401) — bad/missing token; not a DB problem.
- `forbidden` (403) — authz denial; check `membership`/`granted_path` rows, not
  connectivity.
- `invalid_request` (422) — malformed body; `details.fields` names the field.
- `idempotency_key_reused`, `invalid_state_transition`, `consent_required`
  (409) — domain conflicts; data-state issues, not infra.
- 500 / unhandled — the envelope hides DB detail on purpose. Go to service
  logs.

### DB layer (in API/worker logs — psycopg/SQLAlchemy)

- `OperationalError` / connection refused or timeout — wrong host/port,
  IPv6-only direct host on an IPv4 network (switch to session pooler), or
  Supabase project paused.
- `TimeoutError` from the pool — pool exhausted; lower `SMARTMATCH_DB_POOL_*`
  or raise the plan's connection limit.
- SQLSTATE `53300` (too many connections) — hit Supavisor/direct cap; same fix.
- SQLSTATE `42P01` (undefined table) — migrations not run on this database;
  check `alembic_version`.
- SQLSTATE `23505` (unique violation) — real constraint hit; look up the named
  constraint in `schema.py` (`uq_*`, `pk_*` names are interfaces —
  `idempotency.py`, `rate_limit.py`, `events.py`, `match_runs.py`,
  `outreach.py`, `pilot_auth.py` target them in `ON CONFLICT`).
- SQLSTATE `28P01` (auth failed) — wrong password/user; use `postgres.<ref>` as
  user on the pooler, not bare `postgres`.
- "prepared statement … already exists" — you're on transaction-mode pooler
  (6543). Switch to session mode.
- Alembic failure mid-run — earlier revisions already committed
  (`transaction_per_migration`); fix the failing revision and re-run.
  `docs/operations/deploy-runbook.md` owns this procedure.
- Drift test failure — `schema.py` and the migrated DB disagree; the test
  output names the table/constraint. Fix the side that's wrong, never both to
  match.

## Acceptance criteria

- `alembic upgrade head` runs clean on the Supabase project.
- `test_schema_matches_migration.py` passes against Supabase.
- `make test-integration` passes against Supabase.
- `docs/operations/supabase-setup.md` and `supabase-maintenance.md` committed.
- `.env.example` documents the Supabase URL shape and pool settings.
- No Supabase keys, Data API, or RLS in the app path;
  `SMARTMATCH_DATABASE_URL` is the only integration point.
