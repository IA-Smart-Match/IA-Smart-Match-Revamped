# Issues #319 + #271 — instructor per-team detail must show names and the four numbers / result names die when the saved setting is deleted

> Implementation-context brief generated by analysis agent against `main`. For the planning model. **These two issues share one fix** — the run-time invited-profile snapshot — and should land together.

**⚠️ Migration-number collision:** this brief and #318 both plan `0044_*` after `0043_exercise_event_exploratory`; #326 also wants `0044`. Three migrations want the same head — assign 0044/0045/0046 in landing order before branching.

## 1. The shared boundary both issues cross

Both issues are about **one stored record being read through a mutable one**:

- A **saved setting** (`exercise_saved_setting`, `python/smartmatch_persistence/smartmatch_persistence/exercise/schema.py:354-394`) is `(workspace_id, event_key, name)` → `weights` JSONB (`:370`). It can be edited in place (upsert overwrites `weights`, `settings_repository.py:331-415`) and deleted (`exercise_matching.py:672-726`). Max three per event is enforced in `save_setting`.
- A **result run** (`exercise_result_run`, `schema.py:397-443`) is a historical record: `setting_name` (nullable text, deliberately *not* an FK, `:407-411`), `invited_profile_nos`/`signed_up_profile_nos`/`attended_profile_nos` int arrays, `email_everyone` JSONB, `seats_empty`, `created_at`. Unique per `(workspace_id, event_key)` (`:425-428`); composite FKs bind it to the right dataset/workspace/event. It survives setting deletion but stores **no names and no weights snapshot**.
- The run's invited set is computed by `_invited_profile_nos` (`services/api/smartmatch_api/routers/exercise_results_run.py:200-238`) via `rankable_set` + `event_evidence` + `exercise_ranked_list` — **the full ranked entries (`ranked.entries`) are in hand at write time and then discarded** down to `entry.profile_id` ints. This is the natural snapshot seam.
- Everything behind the exercise routes crosses one door: `services/api/smartmatch_api/exercise_dependencies.py` re-exports the persistence rows/repositories (`:108-159`, `__all__` `:167-235`); routers may import nothing else from `smartmatch_persistence` (import-linter contract, `pyproject.toml:309-365`, one ignored edge per repository module `:346-362`). New row types must be re-exported there; a new persistence module needs a new edge line.
- The safe profile projection is `exercise_profile_public_columns()` (`schema.py:483-510`) — every profile column **except** `EXERCISE_WITHHELD_FIELDS` (`smartmatch_domain/exercise/__init__.py`: `hidden_true_interests`, `hidden_true_career_goal`). `TeamProfileRow` (`team_view_repository.py:71-114`) is built on it, so `display_name`/`major`/`class_year` are already the public fields; `marker`/`reason` are derived in `exercise_matching_models.py:291-331` (`rankable_set`, `derive_marker`) and `exercise_ranked_list`.

## 2. Issue #319 — instructor's per-team detail must show names and the four numbers

### Current endpoint and shape

`GET /v1/exercise/instructor/workspaces/{team_number}` — `exercise_instructor.py:491-529`. Behind the router-level `require_instructor_session` gate (`:149-153`), resolves `_teams_dataset` (`:609-665`, "the file the teams are on", never the newest upload) then `_require_team` (`:668-689`), reads `instructor.list_saved_settings` + `instructor.list_result_runs`, and returns `TeamDetailView{team_number, saved_settings, result_runs}` (`exercise_instructor_models.py:273-285`).

- `SavedSettingView` = `{event_key, name, created_at}` only (`:248-255`).
- `ResultRunView` = `{event_key, round, setting_name, invited_count, signed_up_count, attended_count, seats_empty, created_at}` (`:258-270`).
- Rows: `InstructorSavedSetting` (`instructor_rows.py:102-114`, docstring explicitly excludes weights) and `InstructorResultRun` (`:117-134`, explicitly "no profile number"). Queries select names + `cardinality()` counts only (`instructor_repository.py:332-388`).
- Frontend `TeamDetail` (`InstructorTeams.tsx:293-329`) prints `"{name} — for {event_key}"` and `"Round {n} for {event_key}: invited …"`. No weights, no names, no event display name, no linkage.

### What is missing vs. the requirement

Stakeholder text (Progress `:27-30`, Checklist `:41`, `:147`): "its saved settings with the four numbers, its list of names, its results for each event, the way of asking it chose, and whether it has refreshed." Asking choice and refresh state already exist on the **summary** (`InstructorWorkspaceRow.asking_choice/refreshed_at`, `instructor_rows.py:50-66`; rendered at `InstructorTeams.tsx:235-240`). Missing from detail: weights, invited names per setting, names per run, event display names, run→setting linkage.

### Proposed contract (extend the existing endpoint; no new route)

Shared wire model, defined once in `exercise_results_models.py` and reused by the instructor track (cross-router-module import is already the pattern — `exercise_results_run.py` imports `exercise_matching_models`):

```python
class InvitedProfileView(BaseModel):  # the six §7 display fields + rank
    model_config = ConfigDict(extra="forbid")
    rank: int | None = None  # null only on pre-migration rows
    profile_no: int
    display_name: str
    major: str | None = None
    class_year: str | None = None
    marker: str | None = None  # null only on pre-migration rows
    reason: str | None = None
```

- `SavedSettingView` (instructor) gains: `weights: dict[str, float]` (**effective** four via `effective_weights(stored.weights)`, `exercise_matching_weights.py:195-206` — never raw/normalized), `event_name: str`, `round: int | None` (`round_of`, `exercise_results_models.py:124-141`), and `invited: list[InvitedProfileView]` in **rank order**.
- `ResultRunView` gains: `event_name: str`, `invited: list[InvitedProfileView]`, `signed_up: list[InvitedProfileView]`, `attended: list[InvitedProfileView]` (resolved `profile_no`→snapshot; all are subsets of invited), and `setting_weights: dict[str, float] | None` — the weights actually used (see §3). `setting_name` stays as the historical label.
- `TeamDetailView` gains `factor_labels: dict[str, str]` (Ann's words; `_RESPONSE_FACTOR_LABELS`, `exercise_matching_models.py:652-656`) so the UI never prints factor keys. Optional scope: `email_everyone` counts on `ResultRunView` (the comparison is the lesson, and the counts are already stored in the row's JSONB, `schema.py:415-418`).

### Data path

- `list_saved_settings` (`instructor_repository.py:332-350`) additionally selects `exercise_saved_setting.c.weights` → `InstructorSavedSetting.weights`. Docstring `:335` and the type docstring `:104-110` must be rewritten — the "without its weights" contract is what this issue retires.
- `list_result_runs` (`:352-388`) additionally selects the new snapshot column and the three arrays (or the snapshot plus `signed_up`/`attended` nos for the builder to join). This deliberately breaks the "counts in SQL, numbers never fetched" posture (`:355-361`) — D8 forbids score-shaped *numbers*, not names; the guardrail tests are updated accordingly (§5).
- The detail route needs `DatasetRepository` + `TeamViewRepository` injected (both already exist as dependencies — `exercise_dependencies.py`, and `exercise_instructor_refresh.py` is the precedent for instructor routes using them). For each saved setting: `rankable_set(team_view.list_team_profiles(dataset_id=workspace.dataset_id, workspace_id=workspace.id), datasets.list_events(dataset_id=…))` computed **once**, then `exercise_ranked_list(event_evidence(event), rankable.profiles, weights=validated(dict(row.weights)), invite_limit=summary.invite_limit, year_rank=rankable.year_rank, dataset_checksum=summary.checksum)` — i.e. exactly `_invited_profile_nos`'s composition, kept in the same order-of-reads (event resolved before the 300-row join, `exercise_matching.py:196-222`). This composes the ranker, never re-derives it.
- **Live recompute is correct for saved settings** (they are current-state; a snapshot would go stale across the refresh that mutates the overlay, `team_view_repository.py:32-38`). **Only runs snapshot** (they are history).
- The route-table pin `test_exercise_instructor_router.py:1481-1491` must gain `get_dataset_repository` and `get_team_view_repository` for this route — that pin exists precisely to force this edit to be deliberate.
- File budget: `exercise_instructor.py` is 698 lines under an 800-line ceiling pinned by `test_both_instructor_modules_stay_under_the_line_ceiling` (`test_exercise_instructor_router.py:1589-1602`). If the composition doesn't fit, put it in a new `exercise_instructor_detail.py` module — that requires adding the module to `pyproject.toml` `source_modules` (`:312-336`), to `_TRACK_MODULES` (`:1263`), and a note that the ceiling test then covers it. `exercise_instructor_models.py` (410 lines) holds the new/extended models.

### Frontend

## 3. Issue #271 — result names die when the saved setting is deleted

### Bug mechanics (exact)

1. `ExerciseResults.tsx:110-114`: `load()` runs `listForEvent(eventKey, results?.setting_name ?? null)` alongside `readResults`.
2. `listForEvent` (`:161-183`) calls `readRankedList(eventKey, {kind:"setting", name})` → `GET …/list?setting=…` → `_saved_weights_or_refusal` (`exercise_matching.py:157-180`) → `get_setting` returns `None` after `DELETE …/settings/{name}` (`:672-726`) → **404 `exercise_setting_unknown`**.
3. The catch swallows it to `{names: ∅}` (`:175-183` — by design, "a refusal leaves the map empty").
4. `ResultPanels.tsx:230-231`: `names.get(profileNo) ?? \`Profile ${profileNo}\`` — the visible symptom. Backlog `docs/plans/backlog.md:17` describes exactly this.

### Why live lookup is the wrong model

`stored_results_view` says it: the response is "a record, not a recomputation" (`exercise_results_models.py:481-506`). Names asked of a mutable saved setting contradict that. It is also wrong in a second way: even without deletion, a same-name **re-saved** setting returns a different list — the names shown would not be the names the run invited.

### Alternatives

| Option | Verdict |
|---|---|
| **Snapshot the safe projection on the run at write time** | **Chosen.** Serves #271 and supplies #319's run lists; matches `email_everyone`/`seats_empty` "stored, not recomputed" precedent (`schema.py:415-422`). |
| Refuse deleting a setting a run used | Rejected in backlog; breaks the three-slot flow (Checklist `:80` expects delete to work), and still gives no marker/reason/order fidelity. |
| Live-join `invited_profile_nos` → `exercise_profile` at read | Names would survive (profiles are immutable post-ingest), but marker/reason/rank order would silently reflect today's overlay, and it does nothing for `setting_weights`. Insufficient for #319. |

### Data model (chosen)

New migration `0044_*` after `0043_exercise_event_exploratory` (head; `:37-56` is the pattern) — **see collision note at top**. On `exercise_result_run` (`schema.py` mirror in the same change):

- `invited_profiles` `JSONB` nullable — list of `{rank, profile_no, display_name, major, class_year, marker, reason}`, **rank order** (this incidentally fixes backlog `:21` for the snapshot path: today the stored `invited_profile_nos` are number-sorted).
- `setting_weights` `JSONB` nullable — the effective four weights used (delete- and re-save-proof).

**Backfill (existing runs):** the VM deployment (`backlog.md:27`) already carries real runs, and Checklist `:149` notes leftover test work under Teams 1–4 — so NULL is a live state, not a theoretical one. Do a **SQL-only** backfill in the migration: `invited_profiles` ← `jsonb_agg(jsonb_build_object('profile_no',…,'display_name',…,'major',…,'class_year',…) ORDER BY ord)` over `unnest(invited_profile_nos) WITH ORDINALITY` joined to `exercise_profile` on `(dataset_id, profile_no)`; `setting_weights` ← `exercise_saved_setting.weights` joined on `(workspace_id, event_key, name)` where the row survives. `rank`/`marker`/`reason` are **not reconstructible** (they depend on weights + overlay at run time) — leave them absent and let the response model's `| None` defaults carry "recorded before this change" honestly rather than fabricate a rank. Never import domain code in the migration.

### Write/read path

- `exercise_results_run._invited_profile_nos` → return the ranked entries (rename e.g. `_invited_entries`); `invited_list` (`:400-441`) threads them through; `store()` (`:298-321`) passes `invited=` snapshot + `setting_weights=effective_weights(weights)` into `record_run`.
- `results_repository.record_run` (`:376-459`) gains `invited: Sequence[InvitedProfile]`, `setting_weights` params; writes both columns. `_one`/`get_run`/`get_run_for_round` (`:301-330`, `:675-690`) select them into `StoredResultRun`, which gains `invited: tuple[InvitedProfile, ...]` + `setting_weights: Mapping[str,float] | None`. New frozen dataclass `InvitedProfile` in `results_rows.py` (re-export through `exercise_dependencies.__all__`).
- `stored_results_view` adds `ResultsView.invited_profiles: list[InvitedProfileView]` — top level, **not** on `ResultPanelView` (`email_everyone` shares that model and must stay counts-only; the "300-person comparison stays a number" rule, `ResultPanels.tsx:10-21`, `exercise_results_models.py:299-310`). `PreviousRoundView` stays counts-only for the student page; the instructor reads run rows directly for names.
- Delete-flow: nothing changes on `DELETE …/settings/{name}` — which is the point; the run no longer reads it.

### Frontend

`ExerciseResults.tsx`: when `results !== null`, build `names` from `results.invited_profiles` (`Map(profile_no → display_name)`); fetch the ranked list only pre-run for `factor_labels` (the setting cards, `:271-277`, need labels — keep `listForEvent` for that case, `weighting:{kind:"default"}` is fine since labels are constant). `ResultPanels.tsx`: keep `Profile ${n}` only as the defensive fallback for a number the snapshot doesn't name (its docstring `:17-20` already covers "say what is missing"). `exerciseClient.ts`: `ResultsView` gains `invited_profiles`; new `InvitedProfileView` interface (mirror of `ListEntryView` minus factor fields).

## 5. Guardrails that must be amended on purpose

- `test_exercise_instructor_router.py:1247` — `_SCORE_SHAPED` includes `"weight"`, which now conflicts with the required `weights`/`setting_weights` fields. Keep the substring walk for `score|percent|confidence|probability` and **replace "weight" with a positive allowlist**: assert the only weight-bearing fields are exactly `SavedSettingView.weights` and `ResultRunView.setting_weights`, so a *new* weight-shaped field still fails loudly. (`RankedListView.weights` already exists exercise-wide at `exercise_matching_models.py:461-467` and is legitimate — it's the team's own input, the D8-carved exception.)
- Do **not** import `RankedListView`/`ListEntryView` into `exercise_instructor` — `_models()` (`:1266-1275`) walks `vars()` of the instructor modules; imported response models become walked, so keep imports to the helper functions + the new `InvitedProfileView` (whose field names contain no score-shaped substring).
- The results-track served-contract walk (`test_exercise_results_contract.py:225-271`) covers *every* schema reachable under `/v1/exercise` — its `_SCORE_SHAPED` (`:119`) is `score|percent|confidence|probability|likelihood|share` (no `weight`), so `weights`/`setting_weights` pass; but `dataset_id`, `seed`, `token`, withheld names remain forbidden on this track's models — new fields must avoid them.
- `test_exercise_instructor_persistence.py:452-470` asserts `not hasattr(run,'invited_profile_nos')` / `not hasattr(setting,'weights')` — invert into positive assertions for the new fields plus negative assertions that `hidden_true_*`, ids, seeds never appear.
- `test_no_route_response_mentions_the_withheld_column` (`:1312-1321`) and the class-run leak scans (`test_exercise_full_class_run.py:493-509`) must stay green unchanged — they're the proof the new fields leaked nothing.
