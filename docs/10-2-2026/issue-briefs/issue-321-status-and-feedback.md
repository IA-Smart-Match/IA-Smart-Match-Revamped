# Issue #321 — exercise: persistent team/round status + clear action feedback

> Implementation-context brief generated by analysis agent against `main`. For the planning model.

**Verdict:** feasible as one coordinated change; the durable server facts all exist, but `GET /workspaces/current` must grow (or a status aggregate must be added) before any status band can be server-backed. The single clearest functional gap is `RefreshAllPanel` — a class-wide mutation with no confirmation.

## 3. Ordered changes (recommended sequence)

1. **Server-state fields.** Extend `GET /v1/exercise/workspaces/current` (`exercise_workspace.py:284-299`) into the status read, or add `GET …/workspaces/current/status` next to it. Fields: `team_number`, `dataset_label`, `invite_limit` (existing), plus `asking_choice`, `refreshed_at`, and a `rounds[]` array `{event_key, name, round, results_run, results_run_at?}` — optionally `results_open` per round (§5). Requires widening `ExerciseWorkspace`/`_select_one` (`workspace_repository.py:152-173,553`) and composing the events+result-runs read (`ExerciseResultsRepository`, `round_of`). The route is already the reload/second-tab seam; `_view` (`exercise_workspace.py:163-174`) already whitelists fields.
2. **Client types + adapter.** Mirror the new shape in `exerciseClient.ts` (alongside `TeamWorkspaceView` :40-44); keep `readCurrentWorkspace` or add `readWorkspaceStatus`. Never touch `lib/api.ts` (`exerciseApi.ts:29-44`).
3. **Shared status region.** Add a status slot/band to `ExerciseScreen` (between header and `children`), rendered by a `WorkspaceStatus` component fed by a thin `useWorkspaceStatus()` wrapper over `useExerciseResource`. Each page passes its resource's `reload` so mutations refresh the band (`onChanged={reload}` pattern already exists). Design spec §6.1 (`DESIGN.md:342-354`) must gain the band as a stated part of the shell. Include the "not your team? Pick again" affordance (checklist §3:47) or leave it to #268 — see §4.
4. **Per-screen wiring.** Picker, matching, results, asking render the band; entry keeps its existing "already in team N" line. Audit every action for an adjacent persistent message: save ("Saved '{name}'…"), delete ("Deleted…"), compare, run, refresh, choose — new copy goes into §11.1 (`DESIGN.md:851-890`), never invented inline.
5. **Confirmations.** Add `useConfirmWindow`-style or two-button inline confirm to `RefreshAllPanel` (`InstructorUnlock.tsx:357-405`) naming class-wide scope; decide run/refresh confirmations (§5); keep the four existing confirms untouched except shared styling.
6. **Accessibility.** Band text at ≥body size for projector (`ce-type-body`+); once-only buttons remain `aria-disabled` + `describedBy`; status changes announce once via `role="status"`/`aria-live="polite"` (`DESIGN.md:793-795`, `apps/web/DESIGN.md:311`); focus management follows `InstructorUnlock.lifecycle.test.tsx` patterns.
7. **Tests** — §7.
8. **Design-doc amendment.** `docs/design/class-exercise/DESIGN.md`: new band in §6.1/§7 layouts, all new strings in §11.1, any new confirm copy. AGENTS.md rule: the doc is amended in the same change, not violated.

## 5. Decision gates (resolve before implementation)

1. **Extend vs. new endpoint.** Extend `GET /workspaces/current` (one request, already the reload seam) vs. a purpose-built `GET /workspaces/current/status`. Recommendation: **extend** — the response is already "what the cookie points at"; a second endpoint invents a shape the issue doesn't require. Gate: confirm the handler can compose the events/results repositories without violating the router's dependency rules (it currently only takes `CurrentWorkspace`; `exercise_dependencies.py:594-628` already exposes results/team-view repositories).
2. **`refreshed_at` placement.** Add to `AskingStateView` (minimal) or to the workspace status (consolidated). Both need `schema.py`'s `refreshed_at` → repository → view. Also note: **no `asking_chosen_at` exists** — a migration would be needed if "chose at" is ever wanted; checklist only requires the refresh time.
3. **Lock state for teams.** Checklist §5:86 wants the run button grey *before* a press; today the team learns of the lock only via a refused run (`ResultsLockPanel.tsx:4-5` calls this deliberate). Adding `results_open`/`unlocked` to the status read reverses that design choice — needs owner sign-off + §11.1 copy ("Results not open yet"). **Same gate as #328 Gate A — resolve once.**
4. **Confirms on once-only team actions.** Run-results and per-team refresh are once-only; checklist §5:88 explicitly wants "Send this list? You get one results run for Northline" — likely in scope. Refresh is ambiguous — recommend matching the asking-choice arm→press pattern; confirm with the owner.
5. **Post-run disabled button.** "Results already run for this event" as a greyed button means keeping a disabled control mounted after a run (currently unmounted) — small DOM/UX change, aligned with checklist §1:29. **Shared with #328 step 5.**
6. **Status freshness strategy.** Per-page re-read after each mutation (existing `reload` wiring) vs. mutation responses returning the status. Recommendation: reuse `reload` — zero contract churn, consistent with `onChanged`.
7. **Switch-team affordance.** Checklist §3:47 wants a visible path to re-pick. Likely lands in the band ("Team 3 — wrong team?") linking to `/exercise`. Overlaps #268; assign ownership before building.
8. **Instructor page in the band?** Issue says "every team screen"; instructor screens already show per-team state. Recommend excluding the band from `ExerciseInstructor` — confirm.

## 6. Acceptance criteria (issue + checklist, verbatim-verified)

- Every team page (`/exercise/events`, `/exercise/events/:key`, `…/results`, `/exercise/asking`) shows an always-visible status: team number, event/round, results-used, asking choice, refresh state.
- Status is server-backed; survives reload and second tab (`useExerciseResource` semantics; cookie-addressed workspace).
- Success/refusal/no-op messages are adjacent to the control, persist until the next action, and explain no-ops.
- Once-only controls become `aria-disabled` and state why on the button/linked description.
- Reset (done), repoint (done), **refresh-all (new)** state scope and confirm inline — no modals, no `window.confirm`.
- "Refreshed at {time}" is server-derived (`refreshed_at`), not local state.
- Team isolation preserved; no workspace id/seed/token/hidden fields in any response (walked by `test_exercise_workspace_router.py:722-771`).
- Accessibility tests cover live announcements, focus, disabled controls, projector layout.
- Frontend `npm test`, `npm run typecheck`, `npm run build` pass; repo `make check` passes (`Makefile:48-49`).

## 8. Risks

1. **Contract creep on `POST /workspaces`** — the entry response shares `TeamWorkspaceView`; growing it changes what the entry write returns. Keep entry narrow or grow deliberately (`exercise_workspace.py:195-281`).
2. **Aggregate read cost/consistency** — a status read touching workspaces+events+result_runs must be one consistent view; reuse `round_of` (`exercise_results_models.py:124-144`) rather than re-deriving round logic client-side.
3. **Stale band between actions** — mount-time fetch goes stale after a save/run/refresh on the same page; the band must be wired into each page's existing `reload()` (the once-only-button race in `ExerciseAskingForMore.test.tsx:284-358` shows the failure mode).
4. **Reset mid-flight** — instructor reset between a band read and an action: server refusal stays authoritative; band re-read clears it (pattern already proven: `ExerciseAskingForMore.test.tsx:481-516`).
5. **Forbidden-field regression** — adding `id`-adjacent fields risks tripping the model walk; name nothing `id`, `seed`, `token`, or score-shaped (:722-755).
6. **Copy drift** — new sentences must land in §11.1 for Ann's review; hard-coding strings outside the ledger violates the design contract (`DESIGN.md:851-890`, §9:815).
7. **Second-tab divergence** — two tabs both "team 3" is legal (shared workspace, `workspace_token` OQ-CE-08); the band shows server truth in both, so actions in tab A surface in tab B on next read — correct, but worth a test note since checklist §8:123-125 tests it.
