# ADR-0004 — Hand-written Core schema, hand-written migrations, and a declared `ltree` type

**Status:** Accepted
**Date:** 18 August 2026
**Contract:** Architecture v1.1 §2.2, §4.2

## Context

`smartmatch_persistence.schema` needs table definitions to build queries against,
and `db/migrations` needs to shape the database. The usual arrangement derives
one from the other: declare ORM models, run `alembic revision --autogenerate`,
and the migration falls out.

Two things about this schema make that derivation the wrong trade.

**The first is what the schema is for.** Tenant isolation here is structural, not
a column convention. Every tenant-owned table carries a composite unique key
`(tenant_id, id)` — `uq_org_unit_tenant_id`, `uq_user_account_tenant_id`,
`uq_job_tenant_id` — and every foreign key from a tenant-owned child to a
tenant-owned parent is the composite pair that references it. `membership` and
`resource_grant` reference `(tenant_id, user_id)` against
`user_account.(tenant_id, id)`; `job_event`, `outbox_record`, and
`redrive_record` do the same against `job`. A cross-tenant reference is refused
by PostgreSQL, not by an application `WHERE tenant_id = ?` clause that someone
can forget under deadline. That is the mechanism closing audit finding C-02, and
it is the reason `0001_foundation_baseline.py` is worth reading at all.

Autogenerate does not reliably reproduce composite foreign keys, and the failure
mode is silent. A key simplified to a single column still applies cleanly, still
passes every test that does not attempt a cross-tenant write, and has quietly
removed the guarantee the schema exists to provide.

**The second is expand / migrate / contract** (v1.1 §4.2). During the migrate
phase both the old and the new column exist while data moves and two code
versions run side by side. That intermediate state is a *deliberate* divergence
between the model and the database. Autogenerate cannot tell a deliberate
divergence from drift; it reads the extra column as something to clean up and
proposes the destructive contract step while the old release is still serving
traffic. The phase that most needs review is exactly the phase autogeneration
cannot express.

Behind both is a plainer objection: an autogenerated migration is a migration
nobody wrote. Reviewers skim generated diffs. A migration that alters the shape
of the system of record is the last artifact that should be skimmed.

## Decision

Three parts, which only work as a set.

1. Tables are SQLAlchemy **Core** `sa.Table` objects in `schema.py`, written by
   hand. No declarative models and no ORM mapping. The queries in this codebase
   are `sa.select` / `sa.update` / `pg_insert` statements — nothing needs an
   identity map or lazy loading, so the ORM layer would buy nothing and would
   supply the model tree autogeneration wants.
2. Migrations under `db/migrations/versions/` are written by hand.
   `db/migrations/env.py` sets `target_metadata = None`, so autogenerate has
   nothing to compare against and cannot be run by accident.
3. `tests/integration/test_schema_matches_migration.py` compares the code's
   definitions against a freshly migrated database, so drift fails the build
   rather than surfacing later as a `ProgrammingError` inside a request handler.

Structural tenant isolation is recorded **here rather than in its own ADR**,
because it is not a separate decision — it is the reason this one was made. Split
apart, ADR-0004 would state a preference for hand-writing with its justification
filed elsewhere, and the composite-key ADR would state a schema rule with no
account of how it is protected. If the isolation mechanism is ever revisited on
its own terms — row-level security, a separate database per tenant — that
deserves a new ADR superseding this section.

## The `ltree` type

SQLAlchemy ships no `ltree` type, so `LTree(sa.types.UserDefinedType)` is
declared, with `get_col_spec` returning the literal `"ltree"`. It appears twice,
in `schema.py` and again in `0001_foundation_baseline.py`. The duplication is
intentional: a migration is a historical record and must not import a module that
will keep changing after the migration has been applied.

`TEXT` was rejected. `org_unit.path` and `membership.granted_path` exist to be
queried by subtree, and `TEXT` has neither the ancestor/descendant operators nor
the GiST index those operators need — `ix_org_unit_path_gist` and
`ix_membership_path_gist` are `postgresql_using="gist"` and would not be
creatable over text. A path stored as text turns every ancestor query into a
prefix scan, which is not the same capability under a different name.

The declaration covers DDL generation only. It teaches SQLAlchemy's *inspector*
nothing, so reflecting one of these columns produces a warning. Running
`tests/integration/test_schema_matches_migration.py` emits two of them, from the
`inspector.get_columns` call in `test_columns_match`:

```
SAWarning: Did not recognize type 'ltree' of column 'granted_path'
SAWarning: Did not recognize type 'ltree' of column 'path'
```

This is a genuine wart. It is not filtered and should not be: a warning
suppression would also hide the day some *other* column type stops being
recognized, and that would be real drift. Anyone new to the repository will see
these two lines and should be able to find this paragraph rather than
investigate.

## Consequences

**Good.** The isolation guarantee is asserted, not assumed:
`test_tenant_scoped_children_use_composite_foreign_keys` reads the live foreign
keys of `membership`, `resource_grant`, `job_event`, `outbox_record`, and
`redrive_record` and fails if any key touching `tenant_id` is single-column. The
expand-only baseline and the `0002` rate-limit migration were both written to be
read, with the reasoning in their docstrings. Nothing generated them, so nothing
needs to be un-generated when the migrate phase arrives.

**Cost, stated plainly.** There are two definitions of the schema and they must
be kept in step by hand, and the drift test is the only thing that will catch a
mistake. That makes the drift test's coverage the real boundary of the guarantee,
and it is narrower than the arrangement might suggest. It compares table names,
column-name sets, and three specifically named constraints. It does **not**
compare column types, nullability, server defaults, CHECK constraints, or
indexes. The code-side definitions are correspondingly partial — `schema.py`
declares no indexes and no CHECK constraints at all, and `org_unit.tenant_id`
carries a plain `sa.ForeignKey("tenant.id")` where the migration specifies
`ondelete="RESTRICT"`. Divergence along any of those axes is invisible to CI
today. A reviewer who assumes "the drift test covers it" will be wrong about
everything except table and column names.

**Cost.** A schema change is three edits — the migration, `schema.py`, and
whatever asserts the new invariant — instead of one command. This is the intended
friction, not an accident of the approach.

## Alternatives considered

**Declarative ORM models with autogenerated migrations.** Rejected on both counts
above: composite keys are reproduced unreliably and silently, and the migrate
phase cannot be expressed at all.

**Reflection at startup instead of hand-written table definitions.** Rejected. It
removes the second definition and therefore the drift risk, but it also removes
the drift *test*, and it makes the application's understanding of the schema
depend on whatever the database happens to contain — including a half-applied
migration. Reflection would also have to be taught the `ltree` type anyway, since
the inspector does not recognize it.

**A single `ltree` declaration imported by both `schema.py` and the migration.**
Rejected. It removes a duplicated type declaration and couples every past migration to
a module that keeps moving. A migration that changes meaning after it has been
applied is not a record of anything.
