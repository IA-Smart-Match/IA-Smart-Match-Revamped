# Deploy runbook

**Scope:** how schema migrations are applied, what to do when one fails, and
which deployment steps do not exist yet. Written for whoever holds a psql prompt
against a database that matters.

**Nothing in this repository is deployed.** There is no registry, no running
instance, and no applied infrastructure. That is not a gap this document papers
over — the sections below marked *not yet applicable* say what is missing and
what would have to exist first, rather than describing a procedure for
infrastructure nobody can run it against. The only procedure here that has a
real target today is the migration procedure, because a local or CI PostgreSQL
is a real target.

The companion document is [`containers.md`](containers.md), which covers
building and running the two service images.

---

## The one obligation that is easy to miss

**An offline migration script must be applied with `ON_ERROR_STOP` set.**

```
psql -v ON_ERROR_STOP=1 -f upgrade.sql "$PSQL_URL"
```

This is a requirement, not a recommendation, and the reason is in
[ADR-0009](../architecture/decisions/ADR-0009-transaction-per-migration.md). It
is repeated in full under [Applying a generated script](#applying-a-generated-script)
below. If you read nothing else here, read that section.

---

## The migration set as it stands

Four revisions, `0001_foundation` through `0004_lease_and_generation`, which is
head. Migrations are hand-written, not autogenerated (ADR-0004): the composite
tenant-safe keys are the point of the schema, and autogenerate does not reliably
reproduce them.

`db/migrations/env.py` sets `transaction_per_migration=True` on **both** the
online and the offline `context.configure` calls. Every revision is applied in
its own transaction and commits its own `alembic_version` row. Two consequences
run through everything below:

- A lock a revision takes is released when **that revision** ends, not when the
  whole run commits. This matters for `0003`, which takes `ACCESS EXCLUSIVE` on
  `user_account` — a lock that blocks reads, not merely writes, and the API
  resolves a principal out of `user_account` on every authenticated request.
- A multi-step upgrade that fails partway leaves earlier revisions **applied**.
  That state is valid and resumable, not corrupt: `alembic_version` commits with
  its revision, so a failure at `0004` leaves the database at `0003` and saying
  it is at `0003`.

## Applying migrations online

```bash
make migrate        # cd db && ../.venv/bin/alembic upgrade head
```

The target comes from `SMARTMATCH_DATABASE_URL`. `db/alembic.ini` carries a
local default that `env.py` overrides from that variable whenever it is set, so
the same migration set runs against a developer's PostgreSQL, CI's service
container, and any future deployed environment without editing a checked-in
file. **Confirm which database the variable points at before running.**

**If the run fails, re-run `alembic upgrade head`.** Do not assume a failed run
left nothing behind. Fix whatever failed, then run it again; the revisions that
already committed are skipped and the run resumes at the one that did not. This
is the operator obligation ADR-0009 accepts in exchange for releasing locks per
revision, and it only works if someone actually finishes the job.

Verify afterwards:

```sql
SELECT version_num FROM alembic_version;
```

against the head revision id above.

## Generating a script for review

Offline mode emits SQL without opening a connection, which is what makes a
review possible before anything touches the target.

```bash
cd db
../.venv/bin/python -m alembic upgrade base:head --sql > upgrade.sql
```

Notes, all checked against this checkout rather than assumed:

- **Give a range.** `base:head` is for an empty database. For a database already
  at a revision, name it: `0002_rate_limit:head`. Offline mode cannot read
  `alembic_version` to work the starting point out for itself.
- **Alembic's log output goes to stderr**, so redirecting stdout gives clean SQL
  with no `INFO` lines mixed into it. Check the file starts with `BEGIN;`.
- **The script shows the real transaction boundaries.** Today's four revisions
  produce four `BEGIN;`/`COMMIT;` pairs, one per revision, each ending with the
  `INSERT`/`UPDATE` on `alembic_version` for that revision. A reviewed script is
  an honest preview of what the online path does, which is why
  `transaction_per_migration=True` is set on the offline call site as well.
- One `BEGIN`/`COMMIT` per revision is the *containment* property, not an
  equality: a revision using `op.get_context().autocommit_block()` — which
  `CREATE INDEX CONCURRENTLY` requires — emits an extra pair. No revision uses
  one today. `tests/unit/test_migration_transactions.py` pins the property.

### Applying a generated script

```
psql -v ON_ERROR_STOP=1 -f upgrade.sql "$PSQL_URL"
```

**Required. Without it, a failure is silent and the database is left with a
schema ahead of its recorded version.**

The mechanism, from ADR-0009:

`psql` continues after an error by default when reading a file. Under a single
run-wide transaction that was survivable — the first failure poisoned the
transaction, every later statement was refused, and the final `COMMIT` acted as
a rollback, so nothing applied. Per-revision transactions remove that safety
net. A failed revision now rolls back **alone**, and the *next* revision's
transaction runs normally. Its
`UPDATE alembic_version SET version_num = 'N' WHERE version_num = 'N-1'` matches
zero rows — which PostgreSQL does not treat as an error — so that revision's
DDL commits while the recorded version stays behind.

The result is a database whose schema is ahead of its `alembic_version`, with no
failure reported to the operator. This was reproduced against PostgreSQL 16:
after an induced failure in the second of three revisions, the third revision's
table existed and `alembic_version` still read the first.

Two practical points about the connection string:

- `SMARTMATCH_DATABASE_URL` is a **SQLAlchemy** URL and carries a driver suffix
  (`postgresql+psycopg://`). `psql` does not accept that form; use the plain
  `postgresql://` scheme, or the usual `PG*` environment variables. Do not put a
  password on the command line — `psql` reads `~/.pgpass`-style credential
  files and `PGPASSWORD` for that reason, and this repository's secret-scanning
  gates exist to keep credentials out of files that get committed.
- Capture the output. `psql ... | tee upgrade.log` costs nothing and is the only
  record of which statement failed.

## When a revision fails part-way

1. **Stop.** Do not re-run an offline script from the top: it starts at whatever
   revision the range named, and the revisions that already committed will fail
   or, worse, partially re-apply.
2. **Ask the database where it thinks it is.**
   ```sql
   SELECT version_num FROM alembic_version;
   ```
3. **Compare that against the script.** Every revision boundary in the generated
   file is marked `-- Running upgrade <from> -> <to>`. The recorded version tells
   you which boundaries committed.
4. **If you were on the online path**, or on the offline path *with*
   `ON_ERROR_STOP=1`: the recorded version is trustworthy. Fix the cause and run
   `alembic upgrade head` again, or generate a fresh script from the recorded
   revision to head.
5. **If you were on the offline path without `ON_ERROR_STOP=1`**: the recorded
   version is *not* trustworthy, and this is the case that has no shortcut. The
   schema may contain objects from revisions later than the one recorded. Read
   the log to find the first failing statement, then inspect the objects each
   subsequent revision creates and establish, object by object, what is actually
   present. Only then decide whether to complete the remaining work by hand or
   to rebuild. Record what you did; a reconciliation nobody wrote down is
   indistinguishable from drift later on.
6. **Do not edit `alembic_version` to make a problem go away.** It is the one
   row that says what the schema is, and setting it to something the schema does
   not match converts a visible failure into an invisible one.

### Confirming the schema matches the migrations

Two checks exist, and both need a database you are willing to write to:

| Check | Command | What it proves |
|---|---|---|
| Migrations apply cleanly from empty | `make migrate-check` | Creates and drops a scratch database `smartmatch_migcheck`; proves the set applies from nothing |
| The live schema matches the migration | `pytest tests/integration/test_schema_matches_migration.py` | Foreign keys, nullability, types, and PK/UQ/CHECK constraint names, per table |

The integration suite writes rows. Run it against a scratch or development
database only, never against one holding data anyone depends on.

## Rollback

**Roll forward.** Every revision defines a `downgrade()`, and every one of those
functions says in its own docstring that it is present because Alembic expects
it and is usable on a development database — production rollback never depends
on it. Migrations follow expand → migrate → contract (v1.1 §4.2), and the
destructive contract phase runs only after a release is fully promoted and
stable. Backlog item F12 is a contract-phase drop that is deliberately still
waiting for exactly that condition.

A revision must be independently safe under a rolling deploy, because during a
rollout the old and the new release both run against whatever schema is
currently applied. That requirement is what makes "the database sits at any
revision" an acceptable state, and it is a review rule for every new revision.

## Not yet applicable

Each of these is a step a real deploy runbook would have. None can be written
honestly today, because the thing it would operate on does not exist. The
"introduced by" column is what would have to happen first, taken from the
sources named beside it.

| Step | Why it is not here | Introduced by |
|---|---|---|
| Publish an image to a registry | No registry exists or is owned, and no credential binding has been decided. `.github/workflows/build.yml` authenticates to nothing, tags for no registry, pushes nowhere, and requests no permission beyond `contents: read` | A registry and a release policy; the conditions are in that workflow's header |
| Apply infrastructure | `infra/terraform/envs/{dev,staging,classroom,prod}/main.tf` are one comment line each. "Nothing here is deployed, and nothing here should be applied" | Foundation item F5, after containerization |
| Deploy a service, roll traffic, or roll back a release | Nothing is running. The migration contract sets `ALLOW_CLOUD_DEPLOY=false` | Not scheduled |
| Supply provider credentials | No live provider adapter is implemented; construction fails before any credential check. In deployed environments credentials come from Secret Manager, never from a file | The release gate for each provider — G4 for outreach, open decision 6 for routes |
| Configure worker task identity | The verifier is real but ships with no signature backend, no audience, and no service-account allowlist, so it refuses every delivery (`401` without a credential, `501` with one) | Finding S-001: three separate deliberate acts, listed there |
| Schedule the outbox dispatcher | Nothing schedules it at all today, which is backlog item J8 | J8 |
| Monitoring, alerting, on-call | There is no running system to observe and no rotation to page | A deployed environment |
| Smoke test after deploy | The health endpoints exist and are probed in CI against the built images (see `containers.md`), but there is no deployed URL to probe | A deployed environment |

Adding a procedure here for any of the above before the thing exists would make
this document assert something untrue about the repository. When one of them
becomes real, write the section then — and verify it by running it.
